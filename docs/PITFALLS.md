# Подводные камни и соображения

Документ написан до реализации. Цель — зафиксировать, что именно в этой задаче
окажется сложным, и какие решения приняты в MVP (см. `docs/ARCHITECTURE.md`).

Постановка, если коротко: сервер получает путь к каталогу с git-репозиторием,
клиент на React рисует матрицу «коммиты по X × файлы и папки по Y», где
пересечение = коммит затронул файл, прямоугольник по Y = время жизни файла
в репозитории, цвет и иконка = расширение, клик по пересечению = детали.

Все проверки формата вывода git ниже сделаны на живом фикстур-репозитории
(`scripts/make-fixture-repo.sh`), а не по памяти.

---

## 1. Главная проблема: это не Gantt, это разреженная матрица

Диаграмма Ганта — это N строк с одним отрезком каждая. Здесь же на каждой строке
дополнительно лежит до N_коммитов маркеров, то есть объём данных растёт как
произведение, а не как сумма.

Оценка на репозитории среднего размера — 5 000 коммитов и 3 000 файлов:

| Сущность | Количество |
|---|---|
| Ячеек в полной матрице | 15 000 000 |
| Реальных пересечений (в среднем 8 файлов на коммит) | ~40 000 |
| Строк по оси Y (файлы + папки) | ~3 500 |

Выводы, которые определяют всю архитектуру:

- Полную матрицу нельзя ни строить, ни передавать, ни рисовать. Передаём
  **разреженный список изменений** `(индекс_коммита, id_файла, статус)`.
- 40 000 маркеров в DOM/SVG — это уже неработающий интерфейс: в браузере
  комфортный предел порядка 5–10 тысяч узлов, а react-реконсиляция такого дерева
  на каждый zoom/scroll даст секунды на кадр. Значит **Canvas 2D**, а не SVG.
- Ось Y обязана быть виртуализированной, а дерево — свёрнутым по умолчанию.

Отдельно: линейный рост по числу коммитов делает поведение приложения
качественно разным на репозиториях 100, 10 000 и 1 000 000 коммитов (ядро Linux —
1,3 млн). Нужен явный лимит + честное сообщение «показаны последние N коммитов»,
а не молчаливое подвисание.

## 2. Идентичность файла ≠ путь к файлу (самая недооценённая сложность)

В формулировке «прямоугольник начинается, когда файл помещён в репозиторий»
неявно предполагается, что файл — это путь. В git это не так.

Что происходит с прямоугольником:

- **Переименование.** `src/core/app.py` → `src/core/application.py`. Если считать
  путь идентификатором, получаем два прямоугольника-огрызка вместо одной жизни
  файла. Чтобы склеить, нужно детектирование переименований (`-M`), а `--follow`
  работает **только для одного файла за раз** и не масштабируется на весь репозиторий.
- **Перенос каталога.** В фикстуре `git mv src/ui src/interface` дал 5 записей `R100`
  в одном коммите. На диаграмме это «обрыв» — целая ветка дерева умирает и тут же
  рождается рядом. Визуально выглядит как потеря истории, хотя история цела.
- **Удаление и восстановление.** `docs/readme.md` удалён и через месяц создан
  заново. Значит у файла **не один отрезок жизни, а список отрезков с разрывами**.
  Модель «один прямоугольник = один файл» неверна с самого начала.
- **Копирование** (`-C`) даёт статус `C`: у нового файла есть «родитель», но старый
  тоже жив. Дерево идентичностей превращается в граф.

Решение в MVP: сервер проигрывает историю от старых коммитов к новым, ведёт
таблицу «живой путь → id файла», на `R` переносит id на новый путь и запоминает
прежний путь как alias, на `D` закрывает текущий отрезок жизни. Файл получает
стабильный `id` и массив `spans`. Клиент рисует по одному прямоугольнику на span.

Ограничение, которое надо принять осознанно: детектирование переименований в git —
**эвристика по схожести содержимого**, а не факт. Переименование с одновременной
серьёзной правкой не будет распознано (порог по умолчанию 50%), и склейка не
произойдёт. Диаграмма будет иногда «врать» — это свойство данных, не баг.

## 3. История — это DAG, а ось X — прямая

Проектируемая ось X линейна и упорядочена по датам. С git это конфликтует сразу
в нескольких местах.

**Мерж-коммиты не имеют однозначного «списка изменённых файлов».** Проверено на
фикстуре: `git log --name-status` для мержа не выдаёт **ничего** (пустой блок),
а `git show --stat` для того же мержа показывает `src/ui/feature.ts | 1 +`. То есть
`git log` и `git show` по умолчанию расходятся в ответе на вопрос «что изменил этот
коммит». Варианты и их цена:

- ничего не показывать для мержей (по умолчанию в `git log`) — на диаграмме мержи
  выглядят как пустые столбцы;
- `--first-parent`/`-m` — мерж «присваивает» себе все изменения влитой ветки,
  получаем жирный столбец и двойной учёт тех же правок;
- `--cc` — только конфликтные правки, семантически самое честное, но самое
  непонятное пользователю.

В MVP: мержи включаются в ось X, помечаются визуально, изменений не несут; режим
переключаемый. Это осознанный компромисс, который надо показать в легенде.

**Даты ненадёжны.** `AuthorDate` и `CommitDate` расходятся после rebase/cherry-pick,
и сортировка по дате не совпадает с топологическим порядком: родитель может иметь
дату **позже** ребёнка. Встречаются коммиты из 1970 и из будущего (кривые часы,
подделанные даты). Если ось X строится по датам, топология местами будет выглядеть
инвертированной. Нужен переключатель author/commit date и режим «равномерно по
порядку коммитов» вместо реального времени.

**Плотность по времени крайне неравномерна.** Полгода тишины и 40 коммитов за один
вечер — обычная картина. Линейная шкала времени даёт огромные пустоты и слипшиеся
в один пиксель пачки. Нужны оба режима шкалы (ordinal и time) плюс агрегация.

Также: ветки и несколько «голов» на одной оси, shallow clone (`--depth`, история
обрывается искусственно), orphan-ветки, `git replace`/grafts.

## 4. Производительность парсинга git

Ошибка, которая убивает такие проекты: вызывать git по одному разу на коммит
(`git show <sha>` в цикле). 5 000 запусков процесса на Windows — это минуты,
а не секунды. Правильно — **один** вызов `git log` со стриминговым парсером.

Формат вывода, который выбран после проверки на живом репозитории:

```
git log -z --name-status -M -C --pretty=format:'%x01%H%x1f%h%x1f%P%x1f%an%x1f%ae%x1f%at%x1f%ct%x1f%s'
```

Детали, которые пришлось выяснить эмпирически:

- `-z` **обязателен**. Без него git «квотит» неascii-пути (`"\320\272..."`) и ломается
  на путях с пробелами и кавычками. В фикстуре специально есть `src/ui/space in name.ts`,
  `src/ui/quote".ts` и `src/ui/компоненты/кнопка.tsx` — с `-z` они приходят сырыми байтами.
- Структура блока: заголовок, затем `\n`, затем записи `status\0path\0` (для `R`/`C`
  — `status\0old\0new\0`), затем ещё один `\0` как разделитель коммитов. У коммита
  без изменений (мерж) `\n` и записей нет вообще — заголовок сразу закрывается `\0`.
  Парсер обязан обрабатывать оба варианта.
- Статус переименования приходит с процентом схожести: `R100`, `R087`. Букву надо
  отделять от числа.
- **Тема коммита может содержать что угодно**, включая выбранные разделители.
  Наивный `split('\x01')` уязвим к коммиту с `\x01` в сообщении. Защита: проверять,
  что первое поле записи — 40 hex-символов; если нет — это продолжение темы
  предыдущего коммита.

**Кодировки.** Пути в git — это байты, не строки, и не обязательно UTF-8 (особенно
в репозиториях, созданных на Windows в cp1251). Декодирование в UTF-8 необратимо
портит такие пути (U+FFFD), после чего последующий `git show -- <path>` не найдёт
файл. Поэтому сервер хранит **оригинальные байты пути** рядом с `id` файла, а клиент
в запросах деталей ссылается на `fileId`, а не на строку пути.

`--numstat` в тот же поток добавлять не стал: он даёт числа, но не даёт букву
статуса, а совмещение двух блоков в одном `-z`-потоке резко усложняет парсер.
Числа строк подтягиваются лениво при клике.

Кеш: ключ = `HEAD sha + параметры запроса`; инкрементальное обновление делается
как `git log <known_sha>..HEAD`.

## 5. Windows (заказчик указал Windows явно)

- **Разделители путей.** Пользователь введёт `C:\Users\me\proj`, а git всегда
  отдаёт `/`. Нормализация на входе и на выходе, иначе дерево развалится на две
  несовместимые схемы путей.
- **Регистронезависимая ФС.** `src/Utils.ts` и `src/utils.ts` — в git два разных
  файла, на диске один. Такие репозитории существуют, и дерево на них двоится
  (или, наоборот, схлопывается) в зависимости от того, чувствительна ли к регистру
  наша группировка. Решение — группировать строго по байтам git, а расхождение
  показывать как есть.
- **Длинные пути** > 260 символов без `core.longpaths` — часть операций падает.
- **Поиск git.** `git` не гарантированно в `PATH`; типичные места —
  `C:\Program Files\Git\cmd\git.exe`. Нужен параметр конфигурации и понятная
  ошибка вместо `ENOENT`.
- **`safe.directory`.** Если каталог принадлежит другому пользователю, git
  откажется работать с `detected dubious ownership`. Это надо распознать
  и объяснить, а не показывать «unknown error».
- **Antivirus/Defender** замедляет обход большого репозитория в разы; замеры
  производительности на Linux-CI будут оптимистичнее реальности.
- `autocrlf` влияет на числа добавленных/удалённых строк, но не на факт изменения.
- Запуск дочернего процесса **без `shell: true`** (см. следующий раздел) — на
  Windows это ещё и единственный способ не думать про правила квотирования `cmd.exe`.

## 6. Безопасность: тут самая большая дыра

Приложение по замыслу принимает **произвольный путь в файловой системе** и
запускает на нём внешнюю программу. Это два серьёзных класса уязвимостей.

**Инъекция команд.** Если строить командную строку конкатенацией или запускать
через shell, путь `C:\repo & calc.exe` даёт исполнение произвольного кода.
Обязательно: `spawn(gitPath, [args], { cwd })`, `shell: false`, `--` перед путями,
отказ на аргументы, начинающиеся с `-` (иначе `--upload-pack=...` и подобное).

**Чтение произвольных файлов.** Эндпоинт «дай мне историю каталога X» — это
готовый примитив для разведки файловой системы сервера. Пока сервер слушает
`127.0.0.1`, риск ограничен локальной машиной, но:

- bind строго на loopback, не на `0.0.0.0`;
- allowlist корневых каталогов в конфиге;
- проверка через `git rev-parse --git-dir`, что путь — действительно репозиторий;
- разрешение symlink-ов и проверка, что результат не вышел за allowlist.

**Недоверенный репозиторий — это исполняемый код.** Ключевой момент, который
обычно упускают: `.git/config` репозитория может задавать `core.fsmonitor`,
`core.pager`, `core.editor`, `diff.external`, `textconv` — и git запустит эти
программы. Открыть чужой репозиторий = потенциально запустить чужой бинарник.
Меры: `GIT_CONFIG_NOSYSTEM=1`, явное подавление опасных ключей через `-c`,
`--no-optional-locks`, `GIT_TERMINAL_PROMPT=0` (иначе процесс может зависнуть
на запросе пароля), таймаут и `kill` на дочерний процесс.

**DoS.** Огромный репозиторий = минуты CPU и гигабайты JSON. Нужны лимит коммитов,
таймаут, ограничение размера ответа и отмена запроса при уходе клиента.

## 7. Рендеринг и интерфейс

- **Hit-testing.** На Canvas нет DOM-узлов, и клик по маркеру приходится
  разрешать вручную. Наивный перебор 40 000 маркеров на каждое движение мыши даст
  заметный лаг. Нужен обратный пересчёт координат в `(индекс коммита, индекс строки)`
  плюс hash-индекс по этой паре — тогда hit-test это O(1) и hover работает.
- **Синхронизация двух областей.** Дерево слева (DOM, виртуализованное) и канва
  справа обязаны иметь **одинаковую высоту строки и один и тот же скролл**.
  Малейшее расхождение — и точки съезжают на строку, а пользователь получает
  неверную информацию, не заметив этого. Это главный источник «тихих» багов в UI.
- **Слипание по X.** При 5 000 коммитов на 1 200 px один пиксель = 4 коммита.
  Отдельные маркеры неразличимы, нужна агрегация в теплокарту с сохранением
  «есть/нет изменения», и только при zoom-in — отдельные точки.
- **Свёртка папок.** По умолчанию дерево должно быть свёрнуто, у папки —
  агрегированный прямоугольник (от первого до последнего файла внутри) и
  агрегированные маркеры. При разворачивании нужно сохранять позицию скролла,
  иначе пользователь «теряется».
- **Цвет по расширению.** Расширений в реальном проекте десятки. Курируемая палитра
  для популярных (`.py`, `.ts`, `.tsx`, `.js`, `.json`, `.md`, `.css`…) плюс
  детерминированный `hash → HSL` для остальных. Отдельные случаи: файлы без
  расширения (`Makefile`, `LICENSE`) и dotfiles (`.gitignore` — расширение не
  `gitignore`, а «нет расширения»). Плюс доступность: цвет не должен быть
  единственным носителем смысла, статус `A/M/D/R` кодируется формой маркера.
- **Иконки.** Готовые наборы (seti-ui, vscode-icons) — это лицензии и вес бандла.
  В MVP — буквенно-символьные бейджи, без внешнего набора иконок.

## 8. Что ещё сломается на реальных репозиториях

- Пустой репозиторий без коммитов: `git rev-parse HEAD` падает с
  `fatal: ambiguous argument 'HEAD'` (проверено). Нужна отдельная ветка кода.
- `.git` как **файл**, а не каталог (worktree, submodule) — определять через
  `git rev-parse --git-dir`, а не проверкой `existsSync('.git')`.
- Bare-репозиторий: нет рабочего дерева, `--show-toplevel` не работает.
- Detached HEAD: нет имени ветки.
- Submodules приходят как gitlink-записи — это не файлы и не папки, отдельная сущность.
- Git LFS: в истории лежат указатели, размеры и дифы бессмысленны.
- Первый коммит без родителя: все файлы приходят как `A` (проверено).
- Изменение только режима доступа (`chmod +x`) выглядит как `M` без изменений строк.
- Бинарные файлы: `--numstat` даёт `-` вместо чисел, парсер обязан это принять.

## 9. Стек: где можно ошибиться на входе

- **Работа с git.** `nodegit` (libgit2) — нативная сборка, на Windows это
  постоянная боль при установке. `isomorphic-git` — чистый JS, но на больших
  историях кратно медленнее и не даёт `--name-status` в нужном виде.
  Выбор: **тонкая обёртка над git CLI** с собственным стриминговым парсером.
- **Рендер.** SVG проще, но упирается в потолок на первых же реальных данных.
  WebGL избыточен до ~500 тыс. маркеров. Выбор: **Canvas 2D**, с учётом `devicePixelRatio`
  (иначе всё мыльное на HiDPI, что на Windows-ноутбуках с масштабом 150% сразу видно).
- **Клиент-сервер против desktop.** Раз всё локально и под Windows, Electron/Tauri
  избавили бы от класса проблем с безопасностью пути. Заказчик просил клиент-сервер,
  поэтому оставляем HTTP, но с bind на loopback. Стоит держать в голове как
  альтернативу для «продакшена».

## 10. Тестируемость

Без синтетических репозиториев эту логику невозможно проверять: нужны фикстуры
с переименованиями, удалением/восстановлением, юникод-путями, мержами, бинарниками
и mode-change. Скрипт `scripts/make-fixture-repo.sh` создаёт такой репозиторий,
и парсер тестируется против него. CI должен включать `windows-latest`, иначе
именно windows-специфичные проблемы из раздела 5 и всплывут у заказчика.

## Рекомендуемый объём MVP

Включить: линейная ось X по коммитам с двумя режимами шкалы, дерево с виртуализацией
и свёрткой, склейка переименований, отрезки жизни с разрывами, Canvas-рендер,
hover + клик с ленивой загрузкой деталей, цвет по расширению, лимит коммитов.

Отложить: мержи с реальным diff (`--cc`), выбор ветки и отображение DAG, теплокарта
плотности при большом zoom-out, экспорт в PNG/SVG, поиск по файлам, blame,
инкрементальное дообновление кеша, авторская раскраска.

## Открытые вопросы к заказчику

1. Какой порядок величины репозиториев целевой — тысячи коммитов или сотни тысяч?
   От этого зависит, хватит ли Canvas 2D или нужен WebGL и предагрегация на сервере.
2. Мержи: показывать пустыми, или пусть «присваивают» себе влитые изменения?
3. Ось X — реальное время (с пустотами) или равномерно по коммитам? В MVP сделаны
   оба режима, нужен выбор по умолчанию.
4. Сервер только для локальной машины (`127.0.0.1`), или планируется доступ по сети?
   Во втором случае раздел 6 требует полноценной аутентификации и жёсткого allowlist.
5. Нужны ли ветки и переключение между ними, или достаточно истории текущего HEAD?
